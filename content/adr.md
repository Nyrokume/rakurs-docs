Каждое решение записано одинаково: статус, контекст, решение, альтернативы, последствия. «Принято» значит «принято, чтобы начать разработку», а не «навсегда». Пересмотр — только новой записью: прежнее решение остаётся как история и помечается «заменено». Так видно не только что выбрали, но и от чего отказались и почему.

## ADR-001. Rust для агента, Go для сервера {#adr-001}

**Статус:** ~~принято~~ **заменено [ADR-010](#adr-010)** (один язык — Go).

**Контекст.** Агент работает на сотнях и тысячах ПК, использует COM и WinRT (DXGI, Windows.Graphics.Capture), ETW и кодирует изображения. Сервер — приём данных, базы, API консоли.

**Решение (историческое).** Агент — Rust (крейт `windows`), сервер — Go. Разобрано на странице [Стек](stack.html).

**Почему заменено.** Два языка — это двойной найм, два набора CI и мост cgo/FFI на стыке. Для нашего объёма парка предсказуемости Go с аккуратной работой с памятью достаточно, а единый язык резко упрощает разработку и сопровождение. Новое решение — [ADR-010](#adr-010).

## ADR-002. Агент из двух процессов {#adr-002}

**Статус:** принято.

**Контекст.** Службы Windows работают в изолированной сессии 0 и не видят рабочий стол пользователя.

**Решение.** Служба `YasnostAgent` (SYSTEM) отвечает за очередь, сеть, обновления, системную телеметрию и запуск помощника. Помощник `yasnost-session.exe` запускается в каждой интерактивной сессии от имени пользователя и делает снимки, следит за окнами и простоем, показывает трей. Связь — именованный канал с ACL «SYSTEM и владелец сессии».

**Последствия.** Нужно следить за жизнью помощника, обрабатывать быстрое переключение пользователей и RDP. Помощник не имеет сетевого доступа к серверу: всё идёт через службу.

## ADR-003. gRPC поверх HTTP/2 с mTLS {#adr-003}

**Статус:** принято.

**Контекст.** Нужен двунаправленный поток событий, бинарные кадры, взаимная аутентификация агента и сервера, прохождение через корпоративные прокси и балансировщики.

**Решение.** Между агентом и сервером — gRPC (HTTP/2, TLS 1.3), клиентский сертификат на каждый агент, выпускаемый внутренним УЦ при регистрации. Консоль ходит к серверу по REST/JSON. QUIC — кандидат на вторую версию для филиалов с потерями пакетов.

**Последствия.** Нужен свой мини-УЦ и ротация сертификатов. Балансировщик — L4 с пробросом TLS или L7 с поддержкой gRPC и проверкой клиентских сертификатов.

## ADR-004. Хранение: PostgreSQL + ClickHouse + S3 {#adr-004}

**Статус:** ~~принято~~ **заменено [ADR-011](#adr-011)** (PostgreSQL + S3, без ClickHouse).

**Контекст.** Разные профили данных: справочники и политики, события, кадры.

**Решение (историческое).** PostgreSQL для справочников, ClickHouse для событий и текста OCR, S3 для кадров.

**Почему заменено.** Отдельная аналитическая СУБД — это третья система в эксплуатации ради объёмов, которых на старте нет. Для ожидаемого парка PostgreSQL с партициями по дням и полнотекстом (`tsvector` + `pg_trgm`) справляется. Новое решение — [ADR-011](#adr-011).

## ADR-005. OCR на сервере, движок Tesseract {#adr-005}

**Статус:** принято.

**Решение.** Распознавание текста — задача внутри Go-сервера: отдельные воркеры-горутины берут кадры из очереди задач в PostgreSQL и прогоняют их через **Tesseract** (`rus+eng`) через cgo-обёртку. На агенте OCR не делается: нагрузка на ПК пользователя не растёт.

**Последствия.** Серверу нужен CPU под распознавание; при росте парка воркеры масштабируются числом горутин, затем — отдельными инстансами сервера. Языковые пакеты обновляются централизованно.

## ADR-006. Нет канала удалённых команд {#adr-006}

**Статус:** принято.

**Контекст.** Агенты мониторинга часто умеют выполнять команды, скачивать файлы с ПК, блокировать ввод. Это превращает сервер в единую точку компрометации всего парка.

**Решение.** Сервер может передать агенту только (1) подписанную политику и (2) манифест обновления, подписанный отдельным офлайн-ключом. Других команд нет: ни шелла, ни загрузки файлов, ни снимка «прямо сейчас» по запросу. Live view не делаем в первой версии.

**Последствия.** Расследование опирается на то, что уже собрано по политике. Если ИБ нужна более подробная картина по конкретному ПК, она меняет политику для него, и это изменение видно в журнале аудита и сотруднику.

## ADR-007. Трей и окно сотрудника — средствами агента {#adr-007}

**Статус:** принято.

**Решение.** Значок в трее — часть помощника на Go (лёгкая библиотека системного трея), без встроенного браузера. Окно «Что обо мне собирается» помощник отдаёт как локальную страницу (тот же React-интерфейс, что и консоль, собранный в статику) и открывает её в браузере пользователя по умолчанию. Отдельный GUI-движок и WebView не нужны.

**Последствия.** Один набор интерфейсных компонентов на консоль и окно сотрудника. Нет зависимости от WebView2 и тяжёлых GUI-фреймворков.

## ADR-008. Нет кейлоггера, скрытого режима и записи звука {#adr-008}

**Статус:** принято, пересмотру не подлежит без решения руководства и юриста.

**Решение.** Агент не перехватывает ввод с клавиатуры, буфер обмена, микрофон и камеру; не скрывается из трея, списка программ и служб; не использует техники обхода антивирусов. Соответствующего кода в агенте нет.

**Последствия.** Часть сценариев DLP закрывается другими средствами (DLP-шлюз, EDR). Агент проще согласовать с антивирусами, юристом и коллективом. См. [Закон и этика](legal.html).

## ADR-009. Очередь задач — в PostgreSQL {#adr-009}

**Статус:** принято (заменяет прежнее предложение о внешнем брокере).

**Контекст.** Между приёмом кадров и воркерами (OCR, правила, миниатюры) нужна надёжная очередь задач с подтверждениями.

**Решение.** Очередь задач живёт в PostgreSQL: таблица задач, выборка с `FOR UPDATE SKIP LOCKED`, подтверждение по завершении. Отдельный брокер (NATS, Kafka) не вводим — это лишняя система в эксплуатации при наших объёмах.

**Последствия.** Одна база под метаданные, события и очередь. Если поток кадров однажды упрётся в PostgreSQL, вынесение очереди в брокер станет отдельным решением.

## ADR-010. Один язык: Go для агента и сервера {#adr-010}

**Статус:** принято.

**Контекст.** Прежде планировались два языка (Rust-агент, Go-сервер, [ADR-001](#adr-001)). На практике это двойной найм, два CI и мост на стыке. Нужна простота: один язык, понятный путь разработки.

**Решение.** И агент, и сервер — на **Go**. Агент использует `golang.org/x/sys/windows` для Win32 и службы (`.../svc`), реестр через `.../registry`, захват экрана через DXGI Desktop Duplication (через cgo-обёртку или готовую Go-библиотеку захвата — выбор фиксируется на фазе 0 по стабильности и лицензии), ETW — по необходимости. Трей — лёгкая Go-библиотека. Сервер — один модульный монолит на Go. Консоль — React + TypeScript (отдельный слой, собирается в статику). Контракт агент↔сервер — `.proto`-файлы, генерация `grpc-go`.

**Альтернативы.** Rust-агент — отвергнут как второй язык (историческое [ADR-001](#adr-001)). C++ — небезопасная память в процессе SYSTEM на каждом ПК.

**Последствия.** Один найм, один CI, общий код моделей и валидации между частями сервера. За предсказуемой памятью агента следим профилированием и дисциплиной (пулы буферов, явное освобождение нативных ресурсов capture/OCR). Разобрано на странице [Стек](stack.html) и [Как мы строим «Ясность»](build.html).

## ADR-011. Хранение: PostgreSQL + S3 (SeaweedFS) {#adr-011}

**Статус:** принято.

**Контекст.** Два профиля данных: структурированные (ПК, пользователи, политики, роли, события, текст OCR, аудит, очередь) и большие бинарные (кадры).

**Решение.** **PostgreSQL** — всё структурированное: справочники, политики, роли, аудит, события с партиционированием по дням, полнотекстовый поиск по OCR через `tsvector` и `pg_trgm`, очередь задач. **S3-совместимое хранилище** — кадры; по умолчанию **SeaweedFS** (Apache-2.0), для малых инсталляций — локальный диск через тот же интерфейс. ClickHouse не используем.

**Альтернативы.** ClickHouse для событий (историческое [ADR-004](#adr-004)) — отложено: вернёмся к нему, только если флот превысит несколько тысяч ПК и PostgreSQL перестанет держать аналитику. MinIO как новую зависимость не берём (репозиторий Community ушёл в архив).

**Последствия.** Две системы хранения вместо трёх. Для инсталляций до нескольких тысяч ПК этого достаточно; порог пересмотра зафиксирован в [Дорожной карте](roadmap.html).
